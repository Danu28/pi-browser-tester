browser-tester — Simplicity-First Refactor Design

0. One-paragraph diagnosis

The extension works and is well defended — but it has grown a second, parallel implementation of itself. Every browser action exists twice: as a standalone tool (cext_click, cext_fill, …) and as an op inside cext_batch, with two declarations of the same parameter fields and two formatters for the same result line. On top of that sits a stateful body-text diffing layer whose only purpose is to make the duplicated snapshot path cheaper, and two polling loops that wait for things Chrome never does (a respawned service worker, a scannable extension page) — up to 4 s and 10 s of pure waiting per call. The refactor is not about adding structure; it is about collapsing the duplication, deleting the waits, and making cext_batch the single action surface. Everything below is either a deletion or a one-line delegation.

1. How it works today

pi  ──▶ index.ts (505 lines)
          └─ 23 cext_* tools: name/label/description/promptSnippet/parameters/run
               ├─ 14 single-op tools ──┐
               └─ cext_batch ──────────┴─▶ session.batch() ─▶ _batchStep() ─▶ click/fill/… (src/session.js, 803 lines)
                                                                              └─▶ _act() ─▶ _snapshot({dedupe}) ─▶ changedLinesOnly()
        scripts/scenario.mjs  ─────────────▶ session.batch()  (same interpreter, own result formatter)
        scripts/smoke.mjs     ─────────────▶ session.js internals (zero-dependency assertions)
        install.bat           ─────────────▶ copies browser-tester/ to ~/.pi/agent/extensions/browser-tester/

The good parts, which the refactor must not disturb: session.js is pi-free (so npm run check proves it without pi or a browser), cext_batch already is the step interpreter, and scenarios/*.json replays a flow with zero model round trips.

2. Ranked findings

Risk key: high behaviour change / needs a live check · medium needs one verification run · low mechanical.

F1 — 23 tools where 10 suffice high

Evidence. index.ts · tools[]: 23 entries, 505 lines; 23 promptSnippets (985 chars) and 61 description strings (6,481 chars) that ship in every prompt. 14 of those tools are one session method each, wrapped in ~20 lines of schema and prose that batchStep already declares.

Change. Keep 10 tools. Every page action becomes a cext_batch op only:

Keep (10)Why it earns a tool
cext_launchLifecycle + extension side-loading; also the "relaunch fresh" path
cext_reloadExtension-only; relaunches with remembered opts (see F4)
cext_popupComputes chrome-extension://<id>/<default_popup> + the focus-settle dance — a batch op cannot
cext_serveStarts a server; needs cwd from the tool context
cext_batchThe action surface — 15 ops: click, fill, press, select, hover, wait, open, switch, closePage, scroll, history, eval, screenshot, logs, metrics
cext_snapshot1-line alias: batch([{op:"snapshot"}],{snapshot:true})
cext_screenshot1-line alias — humans ask for screenshots by name
cext_logs1-line alias — the most-read diagnostic
cext_cdpEscape hatch; keep until proven unused
cext_closeTeardown — candidate to fold into cext_launch + session_shutdown (see Q3)

Delete as tools (14): cext_open, cext_switch, cext_click, cext_fill, cext_hover, cext_select, cext_press, cext_scroll, cext_eval, cext_wait, cext_metrics, cext_history, cext_close_page — all already batch ops; and cext_reload stays only because it is lifecycle, not an action.

Why simpler. One vocabulary, one interpreter, one place to add an op, ~350 lines and ~5k chars of prompt prose gone. Risk. Agent ergonomics: models reach for cext_click. Mitigation: the three aliases above are one line each and the batch promptGuidelines state the preference (they already do).

F2 — cext_batch cannot scroll or go back high low risk

Evidence. index.ts · batchStep.op oneOf([...13]) and the _batchStep default error both hard-code the same 13 ops; scroll, history, popup, serve, cdp, reload, snapshot, close are standalone-only. This is a recorded landmine: passing {op:"scroll"} is rejected before it runs.

Consequence. Any flow containing a scroll or a back-navigation must break out of the batch and pay an extra round trip — precisely what batch exists to avoid. It is also the blocker for deleting cext_scroll/cext_history in F1.

Change. Add scroll and history to the op list (two _batchStep cases, ~6 lines). Do not add popup/serve/cdp/reload: they need the tool context or are lifecycle. Then publish the list once:

// session.js — single source of truth for the step vocabulary
export const OPS = ["click","fill","press","select","hover","wait","open","switch",
  "closePage","scroll","history","eval","screenshot","logs","metrics"];
// index.ts:  op: oneOf(OPS, "Operation to run")
// _batchStep default:  throw new Error(`unknown batch op: ${step.op} (have ${OPS.join("/")})`)

F3 — The same parameter fields are declared twice medium

Evidence. index.ts · batchStep declares 16 optional fields with prose; each standalone tool re-declares its subset (~120 lines) with slightly different wording.

Change. Derive the surviving tool schemas from batchStep — one description per field, everywhere:

const pick = (names) =>
  Type.Object(Object.fromEntries(names.map((n) => [n, batchStep.properties[n]])));

// cext_screenshot: parameters: pick(["selector","fullPage","inline"])
// cext_logs:       parameters: pick(["level","source","since"])

F4 — cext_reload waits 4 s and then relaunches anyway high low risk

Evidence. session.js · reloadExtension() calls chrome.runtime.reload(), then polls _extensionAlive() for waitMs = 4000 before falling back to this.launch({...this.launchOpts}). The code itself states the reason the fast path never happens: "Chrome does not respawn [a service worker] for a side-loaded unpacked extension" — and --load-extension is the only supported mode.

Change. Make the fallback the implementation. Deletes _extensionAlive, the polling loop, the targets() helper and the fallback flag — ~40 lines and 4 s per reload:

// A side-loaded unpacked extension never respawns its service worker, so the
// only reload that leaves a usable extension is a relaunch with the same opts.
async reloadExtension() {
  if (!this.launchOpts) throw new NotLaunchedError();
  return this.launch(this.launchOpts);
}

Also update smoke.mjs §8: it currently proves the never-taken fast path; it should instead prove "relaunch with the original options".

F5 — Extension-ID scan can burn 10 s; the ID is already computable medium

Evidence. session.js · _resolveExtId() polls _scanExtId() 50 × 200 ms (up to 10 s — every popup-only extension takes all of it) before falling back to _extIdFromPath / _extIdFromKey. Those two are instant, deterministic and already covered by known-answer vectors in smoke.mjs §1–3 (including the Windows drive-letter case).

Change. Compute it; don't hunt for it. Delete _scanExtId + the polling loop (~30 lines):

// Chromium derives an unpacked extension's ID from its path (id_util.cc).
// A manifest "key" overrides it; nothing else does.
_resolveExtId(manifest) {
  return typeof manifest.key === "string"
    ? this._extIdFromKey(manifest.key)
    : this._extIdFromPath(this.extDir);
}

Risk. Medium — verify once on a live launch (one popup-only extension, one with a key) before deleting the scan; keep the ID vectors in smoke.mjs. If a future mode can respawn/renumber, this is the single place to re-add discovery.

F6 — Delete the snapshot diff instead of optimising it high

Evidence. session.js · changedLinesOnly() (~25 lines) + _lastBodyHash/_lastBodyLines + a dedupe flag threaded through _act, _snapshot, batch and all 8 op methods; plus two smoke blocks (§9, §11).

Problem. It is stateful magic output — (unchanged …), … 2 unchanged line(s) above … — that still does not tell the agent what changed, costs two session fields + one flag per op, and exists only to make the duplicated snapshot path (F7) affordable.

Change. Actions never return body text. An action returns one line (3 fill #pass — ok) plus the final url/title. Body text comes only from cext_snapshot or batch(..., {snapshot:true}). Delete changedLinesOnly, both _lastBody* fields, the dedupe option and smoke §9/§11's diff assertions. Cheaper than the diff (0 body chars per action) and stateless. Recommended assertion stays what the README already teaches: end a batch with an eval that returns the values you care about.

F7 — Four layers to run one op medium

Evidence. _act(fn,{snapshot}) → _snapshot({dedupe}) → changedLinesOnly, plus a parallel _mini() for batch, plus a snapshot option on all 8 op methods.

Change. One layer. With F6, snapshot options and _mini disappear:

async _act(fn) {
  const page = await this._ensurePage();
  await fn(page);
  return { url: page.url(), title: await page.title().catch(() => "") };
}

F8 — Two formatters for the same step line low

Evidence. index.ts · batchLine() (5 special cases) vs scripts/scenario.mjs's inline formatter — same i op selector head, same eval → result special case, two places to keep in sync.

Change. Normalise in the interpreter: every _batchStep case returns { result: string }; export one stepLine(r) from session.js (pi-free, so the scenario runner can use it too) and delete batchLine's switch:

export const stepLine = (r) => {
  const head = `${r.i} ${r.op}${r.selector ? ` ${r.selector}` : ""}`;
  return r.error ? `${head} — FAIL: ${r.error}` : `${head} → ${r.result}`;
};

6. Acceptance criteria

  • index.ts ≤ 180 lines (from 505) · src/session.js ≤ 480 (from 803).
  • ≤ 10 registered tools (from 23) · 15 ops, defined by a single exported OPS list used by the schema and the error message.
  • ≤ 2.5k chars of tool description + snippet text in index.ts (from 7.5k).
  • cext_reload latency = relaunch latency (no 4 s wait); a popup-only extension launches with no 10 s scan.
  • npm run check green · both recorded scenarios exit 0 · one live flow driven end to end with cext_batch alone.
  • No new dependencies. scenarios/*.json format unchanged — the two recorded flows replay untouched.

8. Open questions

Q1 — Tool collapse (F1). Is deleting the 13 single-op tools acceptable, i.e. the model must express every action as a cext_batch step? Recommended default: yes, with cext_snapshot/cext_screenshot/cext_logs kept as one-line aliases. If the answer is no, phases 2–3 still apply; only phase 3 stops at "keep the aliases for all 13".
Q2 — Is the extension folder ever npm-installed? If pi install <repo> runs npm install inside browser-tester/, its dependencies.playwright must stay. Recommended default: assume it is never installed (install.bat copies it) but leave the block in place until verified — it costs nothing and is the safer error.
Q3 — Live install: copy or junction? install.bat copying means every edit needs a re-copy (a landmine that has already burned twice). A junction (mklink /J) makes edits live. Recommended default: keep the copy, add the staleness warning (F12) — junctions can surprise git and pi, and mklink may need Developer Mode.
